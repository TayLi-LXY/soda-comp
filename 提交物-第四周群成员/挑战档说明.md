# 群成员管理 · 挑战档说明（成员搜索）

## 选定项

挑战档三选一中选定：**成员搜索**（不做批量导入、不做分页）。

实现为双通道：

| 通道 | 入口 | Mock API | 计数 |
|------|------|----------|------|
| 本会话 | 抽屉顶栏 | `listMembers(conversationId, query)` | 匹配 n / 共 m |
| 历史候选 | 加号 Modal | `searchCandidates(conversationId, query)` | 匹配 n / 共 m（可添加池） |

候选池约 **24** 条历史会话 Agent，本会话种子 **4** 条，检索「搜一下才好找」可感知。

## A. 数据量增长后的影响

当前实现是内存全量扫描，复杂度约 **O(N)**（N = 本会话成员数或可添加候选池大小）。

| 规模 | 表现 | 建议 |
|------|------|------|
| N ≤ 百 | Mock / 本地过滤足够流畅 | 维持现形态即可演示 |
| N 到千级 | 全量下发 + 前端扫会变慢、包体变大 | 服务端索引（名称、角色、来源会话 ID），前端只收一页结果 |
| 历史 Agent 库 ≫ 本会话名单 | **加号检索更先成为瓶颈** | 优先给「跨会话 Agent 库」做检索服务，而不是优化抽屉里几十个头像 |

与进阶规则叠加：每次添加 / 改角色还要扫描「项目角色是否已被占用」→ 也是 **O(N)**。成员变多后，角色唯一性检查应改为 `projectRole → memberId` 索引，否则每次编排都全表扫。

**结论：** 真量级瓶颈在 **历史 Agent 库检索** 与 **角色占用检查**，不在本会话头像条本身。

## B. 成员与角色模型：可扩展范围与瓶颈

| 可扩展 | 瓶颈 |
|--------|------|
| 增项目角色枚举（仍用产品文案体系） | 「同会话角色唯一」过强时，多 Agent 同分工协作会卡死；需产品是否允许多实例 |
| 增来源会话维度 / 标签 | 仅靠标题字符串匹配易误伤；应用 `originSessionId` 精确过滤 |
| 搜索字段扩展（标签、能力） | 无索引时全表扫；跨会话全局库是最大表 |
| Mock 换成真后端 | 权限、`inUse` 必须与任务/调度系统联动，不能只靠前端布尔 |
| 双通道搜索并存 | 两套 N 增长曲线不同，监控与容量规划要分开 |

当前 Mock 适合产品定型前讲清故事与验收；上线后应按「本会话小表 + 历史库大表」分别治理。

## 手工验收（搜索）

| # | 步骤 | 期望 |
|---|------|------|
| 1 | 打开群设置 | 顶栏见「匹配 4 / 共 4」（或当前全量） |
| 2 | 顶栏输入「数据」 | 计数变为匹配 1；列表收窄到 SQL 专家 |
| 3 | 清空顶栏 | 恢复全量 |
| 4 | 点「+」 | 可添加池约二十余条；见「匹配 n / 共 m」 |
| 5 | Modal 输入「库存」 | 匹配数下降，条目来源会话含库存相关 |

录屏：30–60 秒演示双通道搜索与计数，并口述「历史库检索与角色占用检查是规模瓶颈」。
